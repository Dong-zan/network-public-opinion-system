# 网络舆情事件智能分析系统接口协作规范

## 1. 文档说明

本文档用于统一 1 号至 5 号成员之间的数据结构、接口路径和联调边界，作为项目 GitHub 仓库中的协作文档使用。

本规范遵循以下原则：

1. 文档中的 JSON 仅为结构示例，不代表固定数据内容。
2. 真实运行时的事件标题、时间、来源网站、关键词、平台分布、趋势数据等，均应来自真实采集、清洗、分析和聚合结果。
3. 当前前端在开发阶段允许使用 mock 数据进行页面联调与样式开发，但系统整合阶段应以本规范中的接口结构为准。
4. 若字段名、数据类型、接口路径发生变化，必须先同步 1 号成员，再统一通知全组。

---

## 2. 项目目标与模块关系

系统整体目标：

新闻采集 -> 数据清洗 -> 数据库存储 -> NLP 分析 -> 事件聚合 -> AI 增强分析 -> 后端接口 -> 前端展示

成员分工如下：

### 1 号成员：项目负责人 + 后端 + 系统整合

负责：

- 后端框架搭建
- 数据库设计与维护
- 接收 3 号、4 号、5 号模块输出
- 事件聚合与事件级字段生成
- 提供前端接口
- 负责全系统最终联调

### 2 号成员：前端开发负责人

负责：

- 登录页面
- 首页看板
- 舆情事件看板
- 事件详情页
- 智能问答页
- 个人中心
- 与后端接口联调

### 3 号成员：数据采集与清洗负责人

负责：

- 新闻网站/RSS/公开数据源采集
- 原始新闻清洗
- 输出统一新闻结构给后端

### 4 号成员：NLP 分析负责人

负责：

- 关键词提取
- 情感分析
- 热度计算
- 生命周期判断
- 相似新闻辅助聚类

### 5 号成员：AI 功能负责人

负责：

- 事件智能问答
- AI 分析报告生成
- 其他大模型增强功能

## 3. 核心数据 ID 定义

### 3.1 `news_id`

含义：单条新闻唯一编号，由 1 号后端生成。

用途：标识单篇采集新闻，供存储、分析、追踪使用。

### 3.2 `event_id`

含义：舆情事件唯一编号，由 1 号后端在事件聚合阶段生成。

用途：将多篇属于同一事件的新闻聚合为一个舆情事件，供前端列表、详情、AI 分析等页面使用。

说明：

- 同一事件可包含多条新闻。
- 4 号成员输出 `similar_news` 仅作为辅助信息，不直接生成 `event_id`。
- `event_id` 的最终判定和维护由 1 号成员负责。

## 4. 内部模块数据交互规范

本节描述前端以外的内部模块如何向 1 号后端提供数据。

### 4.1 3 号 -> 1 号：新闻采集输出

说明：以下字段为原始新闻标准结构，实际值来自真实采集结果，不固定。

```json
{
  "title": "新闻标题",
  "content": "新闻正文",
  "source": "人民网",
  "url": "https://example.com/news/1001",
  "publish_time": "2026-07-08 10:00:00"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `title` | string | 是 | 新闻标题 |
| `content` | string | 是 | 新闻正文 |
| `source` | string | 是 | 来源网站或来源媒体 |
| `url` | string | 是 | 原文链接 |
| `publish_time` | datetime string | 是 | 新闻发布时间，格式建议为 `YYYY-MM-DD HH:mm:ss` |

### 4.2 4 号 -> 1 号：NLP 分析输出

```json
{
  "news_id": 1001,
  "keywords": ["事故", "救援"],
  "sentiment": {
    "positive": 0.2,
    "neutral": 0.3,
    "negative": 0.5
  },
  "heat_score": 85,
  "stage": "成长期",
  "risk_level": "高",
  "similar_news": [1002, 1003]
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `news_id` | int | 是 | 对应新闻编号 |
| `keywords` | string[] | 是 | 关键词列表 |
| `sentiment` | object | 是 | 情感分析结果 |
| `heat_score` | number | 是 | 热度得分 |
| `stage` | string | 是 | 生命周期阶段 |
| `risk_level` | string | 是 | 风险等级 |
| `similar_news` | int[] | 否 | 相似新闻编号列表，用于辅助事件聚合 |

情感字段统一约定：

- `positive`、`neutral`、`negative` 使用 `0~1` 小数表示。
- 三者之和应尽量接近 `1`。

### 4.3 5 号 AI 模块输入：事件级数据

5 号成员的 AI 模块应由 1 号后端传入完整事件数据，而不是直接读取前端页面。

推荐输入结构：

```json
{
  "event_id": 1,
  "title": "事件名称",
  "summary": "事件摘要",
  "overview": {
    "time": "2026-07-08 至 2026-07-09",
    "location": "事件发生地点",
    "cause": "事件起因",
    "persons": "涉事人物"
  },
  "timeline": [
    {
      "time": "2026-07-08 10:00:00",
      "content": "首次报道"
    }
  ],
  "keywords": ["关键词1", "关键词2"],
  "sentiment": {
    "positive": 0.2,
    "neutral": 0.3,
    "negative": 0.5
  },
  "heat": 85,
  "stage": "高潮期",
  "risk_level": "高"
}
```

## 5. 数据库存储建议

### 5.1 新闻表 `articles`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `news_id` | int | 新闻编号 |
| `title` | string | 标题 |
| `content` | text | 正文 |
| `source` | string | 来源网站 |
| `url` | string | 原文链接 |
| `publish_time` | datetime | 发布时间 |
| `event_id` | int/null | 所属事件编号 |

说明：

- 新闻刚入库时，`event_id` 可为空。
- 事件聚合完成后，再由后端回填 `event_id`。

### 5.2 事件表 `events`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `event_id` | int | 事件编号 |
| `title` | string | 事件标题 |
| `summary` | text | 事件摘要 |
| `heat` | number | 热度指数 |
| `risk_level` | string | 风险等级 |
| `stage` | string | 生命周期 |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |

建议取值：

- `risk_level`：低 / 中 / 高
- `stage`：萌芽期 / 成长期 / 高潮期 / 衰退期

### 5.3 分析表 `analysis`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | 主键 |
| `event_id` | int | 事件编号 |
| `keywords` | string/json | 关键词 |
| `positive` | float | 正面比例 |
| `neutral` | float | 中性比例 |
| `negative` | float | 负面比例 |
| `platform_distribution` | string/json | 平台分布 |

说明：

- 若数据库不方便直接存数组，可存 JSON 字符串。
- 对外返回接口时，应转换为前端可直接使用的结构。

## 6. 前端页面与接口对应关系

当前前端页面结构如下：

- 登录页面
- 首页看板
- 舆情事件看板
- 事件详情页
- 智能问答页
- 个人中心

为了保证页面效果与接口一致，后端应至少支持以下能力。

### 6.1 页面功能与字段依赖

#### 登录页面

需要：

- 用户名登录
- 返回登录是否成功
- 可选返回昵称、账号信息

#### 首页看板

需要：

- 热点事件总数
- 最高热度指数
- 高风险事件数量
- 热点事件速览列表

说明：

首页统计目前由前端根据事件列表自行计算，因此后端只需正确返回事件列表即可。

#### 舆情事件看板

需要展示：

- 事件标题
- 事件摘要
- 热度指数
- 风险等级
- 生命周期
- 更新时间
- 情感占比
- 支持按热度/时间排序

说明：

- 排序当前由前端本地完成。
- 若后端未来支持服务端排序，可扩展查询参数，但当前不是必须。

#### 事件详情页

需要展示：

- 完整事件标题
- 事件摘要与完整事件介绍
- 事件概述：时间、地点、起因、涉事人物
- 关键节点时间线
- 发展趋势图
- 情感分布
- 关键词
- 平台分布
- 事件溯源与关键传播路径
- AI 分析报告

#### 智能问答页

需要：

- 当前事件基础信息
- 用户输入问题
- 返回 AI 生成回答

#### 个人中心

需要：

- 保存用户自定义关注关键词
- 保存用户自定义关注平台

## 7. 前端对外接口规范

统一约定：

- 请求与响应统一使用 JSON。
- 推荐响应外层结构为：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

说明：

- 前端当前已兼容 `data` 包裹结构。
- 若返回 `code != 200`，前端应视为失败。

### 7.1 登录接口

接口：

```http
POST /api/login
```

请求示例：

```json
{
  "username": "90",
  "password": "123456"
}
```

返回示例：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "token": "jwt-token",
    "user": {
      "username": "90",
      "nickname": "90"
    }
  }
}
```

说明：

- 当前前端开发阶段可继续使用 mock 登录。
- 系统整合阶段建议由 1 号成员补齐真实登录接口。

### 7.2 热点事件列表接口

接口：

```http
GET /api/events
```

用途：

- 首页看板
- 舆情事件看板
- 左侧当前事件卡片
- 智能问答页事件切换

返回示例：

```json
{
  "code": 200,
  "message": "success",
  "data": [
    {
      "event_id": 1,
      "title": "事件名称",
      "summary": "事件摘要",
      "heat": 85,
      "risk_level": "高",
      "stage": "高潮期",
      "update_time": "2026-07-08 12:00:00",
      "sentiment": {
        "positive": 0.2,
        "neutral": 0.3,
        "negative": 0.5
      }
    }
  ]
}
```

字段说明：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `event_id` | 是 | 事件 ID |
| `title` | 是 | 事件标题 |
| `summary` | 是 | 事件摘要 |
| `heat` | 是 | 热度指数 |
| `risk_level` | 是 | 风险等级 |
| `stage` | 是 | 生命周期 |
| `update_time` | 是 | 更新时间 |
| `sentiment` | 是 | 情感占比，供看板页面展示 |

特别说明：

- `sentiment` 在当前前端看板页面中已实际使用，因此建议直接在列表接口返回。
- 如果后端暂时难以返回，前端会显示为 0，但页面效果会变差。

### 7.3 事件详情接口

接口：

```http
GET /api/events/{event_id}
```

用途：

- 事件详情页
- 智能问答页中的当前事件信息

返回示例：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "event_id": 1,
    "title": "事件名称",
    "summary": "事件摘要",
    "heat": 85,
    "risk_level": "高",
    "stage": "高潮期",
    "create_time": "2026-07-08 09:30:00",
    "update_time": "2026-07-08 12:00:00",
    "overview": {
      "time": "2026-07-08 至 2026-07-09",
      "location": "事件发生地点",
      "cause": "事件起因",
      "persons": "涉事人物"
    },
    "timeline": [
      {
        "time": "2026-07-08 10:00:00",
        "content": "首次报道"
      },
      {
        "time": "2026-07-08 13:00:00",
        "content": "官方发布回应"
      }
    ],
    "trend": [12, 18, 35, 50, 72, 65, 40],
    "trend_labels": ["07-08", "07-08", "07-08", "07-09", "07-09", "07-09", "07-09"],
    "trend_highlights": [0, 3, 4],
    "keywords": ["事故", "救援"],
    "sentiment": {
      "positive": 0.2,
      "neutral": 0.3,
      "negative": 0.5
    },
    "platform_distribution": [
      {
        "name": "微博",
        "value": 32
      },
      {
        "name": "新闻网站",
        "value": 25
      }
    ],
    "propagation_path": [
      {
        "stage": "初始爆料",
        "label": "首个账号发布相关内容",
        "time": "2026-07-08 09:10:00"
      },
      {
        "stage": "媒体介入",
        "label": "媒体开始集中报道",
        "time": "2026-07-08 11:30:00"
      },
      {
        "stage": "官方回应",
        "label": "官方发布回应",
        "time": "2026-07-08 13:00:00"
      }
    ],
    "ai_report": "AI分析报告内容"
  }
}
```

字段约束：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `event_id` | 是 | 事件编号 |
| `title` | 是 | 事件标题 |
| `summary` | 是 | 事件摘要 |
| `heat` | 是 | 热度指数 |
| `risk_level` | 是 | 风险等级 |
| `stage` | 是 | 生命周期 |
| `create_time` | 否 | 创建时间 |
| `update_time` | 是 | 更新时间 |
| `overview` | 是 | 事件概述对象 |
| `timeline` | 是 | 时间线数组 |
| `trend` | 是 | 趋势数值数组 |
| `trend_labels` | 是 | 趋势横轴标签数组，长度需与 `trend` 一致 |
| `trend_highlights` | 否 | 趋势图关键节点下标数组 |
| `keywords` | 是 | 关键词数组 |
| `sentiment` | 是 | 情感分布 |
| `platform_distribution` | 是 | 平台分布 |
| `propagation_path` | 建议提供 | 传播路径，建议在答辩版本中补齐 |
| `ai_report` | 建议提供 | AI 分析报告，建议由 5 号或后端整合输出 |

特别说明：

- `summary` 会被前端用于事件完整介绍文案拼接，因此不能省略。
- `overview` 中的 `time`、`location`、`cause`、`persons` 应尽量返回真实事件信息。
- `timeline` 推荐按时间升序返回。
- `trend_highlights` 存放的是 `trend` 数组中的关键节点下标，例如 `[0, 3, 4]`。
- `platform_distribution` 推荐返回数组，不建议前端再解析长字符串。
- `propagation_path` 与 `ai_report` 虽然前端可做占位，但如果缺失，事件详情页会明显弱化。

### 7.4 个人中心配置保存接口

接口：

```http
POST /api/user/preferences
```

请求示例：

```json
{
  "keywords": ["人工智能", "网络安全"],
  "platforms": ["新闻网站", "微博"]
}
```

返回示例：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "success": true
  }
}
```

说明：

- `keywords` 和 `platforms` 均为字符串数组。
- 前端允许用户自定义输入，不是固定选项。

### 7.5 AI 智能问答接口

接口：

```http
POST /api/ai/ask
```

请求示例：

```json
{
  "eventId": "1",
  "title": "事件名称",
  "summary": "事件摘要",
  "question": "这个事件的主要风险点是什么？"
}
```

返回示例：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "answer": "AI 生成回答"
  }
}
```

说明：

- 当前前端已预留智能问答页面。
- 该接口建议由 5 号成员实现核心能力，1 号成员负责统一接入后端。
- 如果暂时无法接入大模型，可先返回规则模板或测试数据，待第二阶段替换为真实 AI 能力。

为兼顾当前前端页面效果与其他成员开发节奏，联调优先级建议如下。

## 9. 对各成员的具体协调要求

### 对 1 号成员

需要确认：

- 最终接口路径是否采用本规范中的路径
- 字段名是否统一采用本规范中的命名
- 哪些字段由后端直接生成，哪些字段由 3 号、4 号、5 号模块提供后整合
- 第一阶段无法返回的字段，是否先返回空数组、空字符串或占位内容

### 对 3 号成员

需要保证原始新闻数据至少包含：

- 标题 `title`
- 正文 `content`
- 来源 `source`
- 链接 `url`
- 发布时间 `publish_time`

说明：

这些字段会影响后续时间线、来源展示、事件概述和趋势分析的可靠性。

### 对 4 号成员

需要保证输出结果至少包含：

- `keywords`
- `sentiment`
- `heat_score`
- `stage`
- `risk_level`
- `similar_news`

说明：

前端看板页面已直接依赖热度、风险、阶段、情感比例等结果。

### 对 5 号成员

需要确认：

- 是否提供 `ai_report`
- 是否实现 `POST /api/ai/ask`
- AI 回答是直接返回纯文本，还是后续扩展多字段结构

建议：

第一版先返回纯文本 `answer`，这样前后端联调最简单。

## 10. 开发与提交规则

1. 所有模块统一使用 JSON 结构。
2. 各成员之间不直接耦合代码，通过接口或数据库协作。
3. GitHub 提交时应优先保证字段名、结构、说明文档一致。
4. 若修改接口规范，必须同步到群内并通知 1 号成员确认。
5. 前端使用 mock 数据仅用于开发和页面演示，不等于最终系统数据。

## 11. 最终说明
