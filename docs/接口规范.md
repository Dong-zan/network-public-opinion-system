# 二、核心数据关系


系统中存在两个核心ID：

---

# 1. news_id


含义：

单条新闻编号。


生成者：

1号后端。


作用：

唯一标识一篇新闻。


例如：

news_id = 1001

表示：

某网站采集的一篇新闻。

---

# 2. event_id


含义：

舆情事件编号。


生成者：

1号后端。


生成逻辑：

后端根据：

- NLP返回的关键词
- 新闻相似度
- 发布时间
- 新闻内容

判断新闻是否属于已有事件。


如果：

属于已有事件：

复用已有event_id

如果：

属于新事件：

创建新的event_id

例如：

event_id = 5

包含：

news_id 1001

news_id 1002

news_id 1003

表示：

多篇新闻属于同一个舆情事件。

# 三、数据库设计


## 1. 新闻表 articles


保存原始新闻。


字段：

| 字段         | 类型     | 说明         |
| ------------ | -------- | ------------ |
| news_id      | int      | 新闻编号     |
| title        | string   | 标题         |
| content      | text     | 正文         |
| source       | string   | 来源网站     |
| url          | string   | 新闻链接     |
| publish_time | datetime | 发布时间     |
| event_id     | int      | 所属事件编号 |


说明：

新闻刚采集时：

event_id = null

经过NLP分析和事件聚合后：

由后端填入event_id。

---

# 2. 事件表 events


保存聚合后的热点事件。


字段：

| 字段        | 类型     | 说明     |
| ----------- | -------- | -------- |
| event_id    | int      | 事件编号 |
| title       | string   | 事件标题 |
| summary     | text     | 事件摘要 |
| heat        | float    | 热度指数 |
| risk_level  | string   | 风险等级 |
| stage       | string   | 生命周期 |
| create_time | datetime | 创建时间 |
| update_time | datetime | 更新时间 |


risk_level：

低

中

高

stage：

萌芽期

成长期

高潮期

衰退期

---

# 3. 分析表 analysis


保存事件分析结果。


字段：

| 字段                  | 类型   | 说明     |
| --------------------- | ------ | -------- |
| id                    | int    | 编号     |
| event_id              | int    | 事件编号 |
| keywords              | string | 关键词   |
| positive              | float  | 正面比例 |
| neutral               | float  | 中性比例 |
| negative              | float  | 负面比例 |
| platform_distribution | string | 平台分布 |


## 情感字段存储规则


数据库统一使用：

0~1的小数

例如：

```json
{
    "positive":0.2,
    "neutral":0.3,
    "negative":0.5
}
```

前端展示时转换为：

20%

30%

50%

# 五、实时更新机制

系统采用定时任务实现准实时舆情更新。

流程：

```
定时任务启动

↓

3号采集最新新闻

↓

1号生成news_id并保存

↓

4号分析新增新闻

↓

1号更新事件信息

↓

5号生成AI分析

↓

前端刷新数据
```

默认更新周期：

```
10分钟一次
```

实际部署时：

可根据数据源情况调整。
