# 网络舆情事件智能分析系统接口协作规范 4.0

## 1. 文档说明

本文档用于统一 1 号至 5 号成员之间的数据结构、接口路径、模块调用方向和联调边界，作为项目 GitHub 仓库中的正式协作文档使用。


本规范遵循以下原则：

1. 文档中的 JSON 仅为结构示例，不代表固定业务内容。
2. 真实运行时的事件标题、时间、来源网站、关键词、平台分布、趋势数据、传播节点等，均应来自真实采集、清洗、分析和聚合结果。
3. 前端在开发阶段允许使用 mock 数据进行页面联调与样式开发，系统整合阶段应以本规范中的接口结构为准。
4. 5 号 AI 模块输入分为基础必需字段、推荐字段、增强可选字段。
5. 5 号必须根据字段完整度自动降级，数据不足时输出“信息不足”、降低置信度或说明限制，不得编造事实。
6. 若字段名、数据类型、接口路径发生变化，必须先同步 1 号成员，再统一通知全组。

## 2. 成员职责

### 2.1 1 号：后端、数据库、事件聚合、系统整合

负责：

- 后端公开 API。
- 数据库设计与维护。
- 接收 3 号新闻数据。
- 接收 4 号 NLP 分析结果。
- 生成 `news_id`。
- 生成和维护 `event_id`。
- 事件聚合。
- 组装事件详情基础数据。
- 调用 5 号 AI 模块。
- 保存或缓存 AI 报告。
- 保存或缓存 5 号生成的 `overview`、`authenticity`、`propagation_analysis`、`propagation_path`。
- 对前端返回统一响应。

1 号不负责理解性生成 `overview`、虚假文本检测结论或传播路径分析结论。1 号只负责基于数据库和上游结果组装事实字段，并负责调用 5 号生成 AI 派生字段。

### 2.2  2 号：前端展示

负责：

- 登录页面。
- 首页看板。
- 舆情事件看板。
- 事件详情页。
- 智能问答页。
- 个人中心。
- 展示 AI 回答、AI 报告、AI 事件概述、真实性提示、传播路径分析。


### 2.3 3 号：新闻采集与清洗

负责：

- 新闻网站、RSS、公开数据源采集。
- 原始新闻清洗。
- 向 1 号后端输出统一新闻结构。

### 2.4 4 号：NLP 分析

负责：

- 文本预处理和字段标准化。
- 关键词提取。
- 摘要生成。
- 情感分析。
- 热度计算。
- 生命周期判断。
- 风险等级计算。
- 相似新闻辅助聚合。

4 号不负责生成 `event_id`、`overview`、`ai_report`、`authenticity`、`propagation_analysis` 或 `propagation_path`。

4 号输出的是新闻级 NLP 分析结果，其中 `similar_news` 仅作为 1 号后端进行事件聚合的辅助信号，不代表 4 号已经完成最终事件聚合。

4 号模块必须依赖 `jieba`、`SnowNLP` 和 `scikit-learn`。如果依赖缺失，模块应抛出 `AnalysisDependencyError` 并中止本次分析，不返回半成品分析结果。

### 2.5 5 号：AI 功能

负责：

- 基于事件上下文的智能问答。
- AI 事件概述生成，即 `overview`。
- AI 舆情报告生成。
- 虚假文本检测与可信度解释，即 `authenticity`。
- 事件溯源与关键传播路径分析，即 `propagation_analysis` 和 `propagation_path`。
- 对上游结构化结果进行解释。

5 号生成的字段属于 AI 派生字段。5 号只能基于 1 号传入的事件上下文生成，不得编造输入中不存在的人物、地点、原因、时间、来源、账号或传播关系。

### 2.6 成员交付速查

| 成员 | 交付内容 | 不负责内容 |
| --- | --- | --- |
| 1 号 | `news_id`、`event_id`、事件聚合、事件基础数据、数据库表、前端公开接口、调用 5 号、保存 AI 派生结果 | 不生成 AI 理解性结论，不直接做虚假检测或传播路径分析 |
| 2 号 | 展示事件列表、事件详情、AI 问答、AI 报告、真实性提示、传播路径图 | 不生成业务数据 |
| 3 号 | `title`、`content`、`source`、`url`、`publish_time`；增强字段如 `platform`、账号和互动量可选提供 | 不负责事件聚合、NLP 分析、AI 判断 |
| 4 号 | `summary`、`processed_text`、`source`、`publish_time`、`url`、`missing_fields`、`keywords`、`sentiment`、`heat_score`、`stage`、`risk_level`、`similar_news` | 不生成 `event_id`、`overview`、AI 报告、真实性判断、传播路径分析；缺少 `jieba`、`SnowNLP` 或 `scikit-learn` 时不做兜底分析 |
| 5 号 | `answer`、`overview`、`ai_report`、`authenticity`、`propagation_analysis`、`propagation_path` | 不生成或补造新闻事实、数据库 ID、NLP 指标、真实传播关系 |

## 3. 字段命名和单位统一

### 3.1 ID 命名

系统内部、后端接口、AI 模块统一使用：

- `news_id`
- `event_id`

### 3.2 情感字段

`sentiment` 统一使用 `0~1` 小数。

```json
{
  "positive": 0.2,
  "neutral": 0.3,
  "negative": 0.5
}
```

约束：

- `positive`、`neutral`、`negative` 均为 number。
- 取值范围为 `0 <= value <= 1`。
- 三者之和应尽量接近 `1`。
- 前端展示百分比时自行转换或由 1 号后端转换展示文本。

### 3.3 热度字段

4 号输出给 1 号时使用：

- `heat_score`

1 号聚合为事件级数据后，对前端和 5 号统一使用：

- `heat`

5 号只接收和解释 `heat`，不接收 `heat_score`，不计算热度。

4 号 `heat_score` 当前计算口径：

```text
similar_score = min(len(similar_news) * 25, 100)
keyword_score = min(sensitive_hits * 25, 100)
sentiment_score = min(max(positive, negative) * 100 + min(positive, negative) * 40, 100)

heat_score = similar_score * 0.45 + keyword_score * 0.25 + sentiment_score * 0.30
```

说明：

- `similar_score` 表示相似新闻数量带来的传播范围得分。
- `keyword_score` 表示敏感关键词命中得分。
- `sentiment_score` 表示情绪强度得分，强正面和强负面都可以提高热度。
- 热度不等同于风险；风险等级仍重点参考负面情绪。

### 3.4 生命周期字段

`stage` 合法值固定为：

- `萌芽期`
- `成长期`
- `高潮期`
- `衰退期`

4 号负责计算 `stage`。

### 3.5 风险等级字段

`risk_level` 合法值固定为：

- `低`
- `中`
- `高`

4 号负责计算 `risk_level`。

5 号负责解释 `risk_level` 的含义，不得重新计算或覆盖。

## 4. 3 号 -> 1 号：新闻采集输出

```json
{
  "title": "新闻标题",
  "content": "新闻正文",
  "source": "人民网",
  "url": "https://example.com/news/1001",
  "publish_time": "2026-07-08 10:00:00",
  "platform": "新闻网站",
  "author": "作者或账号名称",
  "account_id": "",
  "account_name": "",
  "account_type": "",
  "is_official": false,
  "crawl_time": "2026-07-08 10:05:00",
  "repost_count": 0,
  "comment_count": 0,
  "like_count": 0,
  "reference_urls": []
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `title` | string | 是 | 新闻标题 |
| `content` | string | 是 | 新闻正文 |
| `source` | string | 是 | 来源网站或来源媒体 |
| `url` | string | 是 | 原文链接 |
| `publish_time` | string | 是 | 新闻发布时间，格式为 `YYYY-MM-DD HH:mm:ss` |
| `platform` | string | 否 | 平台名称，如新闻网站、微博、公众号等 |
| `author` | string | 否 | 作者或发布账号 |
| `account_id` | string | 否 | 平台账号 ID，采不到时为空字符串 |
| `account_name` | string | 否 | 平台账号名称，采不到时为空字符串 |
| `account_type` | string | 否 | 账号类型，如普通用户、大V、媒体、官方机构；采不到时为空字符串 |
| `is_official` | boolean | 否 | 是否官方账号或权威来源；无法判断时为 `false` |
| `crawl_time` | string | 否 | 采集时间 |
| `repost_count` | number | 否 | 转发量或转载量，采不到时为 `0` |
| `comment_count` | number | 否 | 评论量，采不到时为 `0` |
| `like_count` | number | 否 | 点赞量，采不到时为 `0` |
| `reference_urls` | string[] | 否 | 正文中引用或提到的链接，采不到时为空数组 |

约束：

- `content` 应尽量为正文全文。
- 若无法获取全文，应提供可用于理解事件的正文摘要，但字段名仍为 `content`。
- `source` 和 `url` 必须来自真实采集结果，不得伪造。
- 无法获得准确 `publish_time` 时，应由 3 号明确告知 1 号，不得伪造发布时间。
- 可选增强字段不阻塞第一版联调。3 号采不到时按上表默认空值返回，5 号会据此降低置信度或说明限制。

## 5. 4 号 -> 1 号：NLP 分析输出

### 5.1 4 号模块调用输入

1 号后端调用 4 号 analysis 模块时，单条新闻建议传入以下结构：

```json
{
  "news_id": 1001,
  "title": "新闻标题",
  "content": "新闻正文",
  "source": "新闻来源平台",
  "publish_time": "2026-07-09 10:30:00",
  "url": "https://example.com/news/1001"
}
```

辅助参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `all_news` | object[] | 否 | 同一批候选新闻，用于计算 `similar_news`。缺省时只分析当前新闻。 |
| `previous_heat_score` | number/null | 否 | 当前新闻或事件上一轮热度，用于辅助判断是否进入衰退期。 |
| `previous_heat_scores` | object | 否 | 批量分析时使用，形如 `{1001: 80}`，key 为 `news_id`，value 为历史热度。 |

### 5.2 4 号模块输出结构

```json
{
  "news_id": 1001,
  "summary": "该新闻主要描述某地突发事件及其后续处置情况。",
  "processed_text": "清洗并合并后的标题正文",
  "source": "人民网",
  "publish_time": "2026-07-09 10:30:00",
  "url": "https://example.com/news/1001",
  "missing_fields": [],
  "keywords": ["事故", "救援"],
  "sentiment": {
    "positive": 0.2,
    "neutral": 0.3,
    "negative": 0.5
  },
  "heat_score": 85,
  "stage": "成长期",
  "risk_level": "高",
  "similar_news": [1002, 1003]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `news_id` | int/string | 是 | 对应新闻编号，原样返回。 |
| `summary` | string | 是 | 4 号生成的新闻摘要，供后端保存，也可作为 5 号 AI 报告和问答的上游上下文。 |
| `processed_text` | string | 是 | 清洗并合并后的标题正文，供后端调试、存储或后续分析使用。 |
| `source` | string | 是 | 标准化后的新闻来源。 |
| `publish_time` | string | 是 | 标准化后的发布时间。 |
| `url` | string | 是 | 标准化后的新闻链接。 |
| `missing_fields` | string[] | 是 | 当前新闻缺失字段列表，用于提示 1 号后端或 3 号爬虫补齐数据。 |
| `keywords` | string[] | 是 | 关键词列表。 |
| `sentiment` | object | 是 | 情感分析结果，使用 `0~1` 小数，包含 `positive`、`neutral`、`negative`。 |
| `heat_score` | number | 是 | 新闻级热度得分，范围 0 到 100。 |
| `stage` | string | 是 | 生命周期阶段，合法值为 `萌芽期`、`成长期`、`高潮期`、`衰退期`。 |
| `risk_level` | string | 是 | 风险等级，合法值为 `低`、`中`、`高`。 |
| `similar_news` | int[]/string[] | 否 | 相似新闻编号列表，用于辅助 1 号后端事件聚合。 |

### 5.3 依赖和错误处理

4 号 analysis 模块必须安装以下依赖：

```text
jieba
snownlp
scikit-learn
```

依赖安装命令：

```powershell
python -m pip install jieba snownlp scikit-learn
```

约束：

- 如果缺少 `jieba`、`SnowNLP` 或 `scikit-learn`，4 号模块抛出 `AnalysisDependencyError`。
- 缺依赖时不返回 `keywords`、`sentiment`、`heat_score` 等半成品字段。
- 后端可以捕获 `AnalysisDependencyError`，向控制台或前端提示先安装依赖。
- 4 号不再使用第三方库缺失时的简单规则兜底方案。

错误示例：

```json
{
  "success": false,
  "message": "analysis 模块缺少必要依赖：jieba、snownlp。请先安装 jieba、snownlp、scikit-learn 后再运行分析。"
}
```

### 5.4 边界约束

- 4 号不生成 `event_id`。
- 1 号根据 `similar_news`、关键词、时间、内容等信息完成事件聚合。
- `similar_news` 是辅助聚合信号，不是最终事件聚合结果。
- 5 号不得重新运行或复制 4 号算法。
- 4 号不需要为 4.0 额外生成 `overview`、`timeline`、`trend`、`platform_distribution`、`authenticity`、`propagation_analysis` 或 `propagation_path`。
- 4 号输出的 `summary`、`keywords`、`sentiment`、`heat_score`、`stage`、`risk_level`、`similar_news` 可以作为 5 号生成 AI 派生字段的重要上游依据。

## 6. 1 号 -> 5 号：AI 事件上下文

为避免给 1 号、3 号、4 号增加过多额外开发负担，5 号 AI 模块输入字段分为三类：

1. 基础必需字段：保证 5 号可以启动智能问答、AI 报告、初步真实性提示和弱传播路径分析。
2. 推荐字段：提升 AI 输出质量。
3. 增强可选字段：用于高质量虚假文本检测和真实传播链路分析，第一版不强制提供。

5 号必须能在只有基础必需字段时运行。推荐字段或增强字段缺失时，5 号必须降低置信度，并在 `warnings` 或 `limitations` 中说明数据不足，不得编造输入中不存在的新闻、账号、来源、时间或传播关系。

说明：`overview` 为可选字段，仅当 1 号已有缓存的 5 号 AI 事件概述时传入；首次调用 5 号时可省略。

```json
{
  "event_id": 1,
  "title": "事件名称",
  "summary": "事件摘要",
  "overview": {
    "time": "2026-07-08 至 2026-07-09",
    "location": "事件发生地点",
    "cause": "事件起因",
    "persons": "涉事人物"
  },
  "timeline": [
    {
      "time": "2026-07-08 10:00:00",
      "content": "首次报道"
    }
  ],
  "keywords": ["事故", "救援"],
  "sentiment": {
    "positive": 0.2,
    "neutral": 0.3,
    "negative": 0.5
  },
  "heat": 85,
  "stage": "高潮期",
  "risk_level": "高",
  "update_time": "2026-07-08 12:00:00",
  "articles": [
    {
      "news_id": 1001,
      "title": "新闻标题",
      "source": "人民网",
      "url": "https://example.com/news/1001",
      "publish_time": "2026-07-08 10:00:00",
      "content": "新闻正文"
    }
  ],
  "trend": [12, 18, 35, 50, 72, 65, 40],
  "trend_labels": ["07-08", "07-08", "07-08", "07-09", "07-09", "07-09", "07-09"],
  "platform_distribution": [
    {
      "name": "微博",
      "value": 32
    },
    {
      "name": "新闻网站",
      "value": 25
    }
  ],
  "enhancement": {
    "account_fields_available": false,
    "interaction_fields_available": false,
    "propagation_edges_available": false
  }
}
```

### 6.1 基础必需字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `event_id` | int | 是 | 事件编号 |
| `title` | string | 是 | 事件标题 |
| `summary` | string | 是 | 事件摘要 |
| `keywords` | string[] | 是，可为空数组 | 关键词 |
| `sentiment` | object | 是 | 情感分布，使用 `0~1` 小数 |
| `heat` | number | 是 | 事件级热度 |
| `stage` | string | 是 | 生命周期 |
| `risk_level` | string | 是 | 风险等级 |
| `update_time` | string | 是 | 事件最后更新时间 |
| `articles` | object[] | 是，可为空数组 | 与事件相关的新闻列表 |
| `articles[].news_id` | int | 是 | 新闻编号 |
| `articles[].title` | string | 是 | 新闻标题 |
| `articles[].source` | string | 是 | 来源媒体 |
| `articles[].url` | string | 是 | 原文链接 |
| `articles[].publish_time` | string | 是 | 发布时间 |
| `articles[].content` | string | 是 | 新闻正文或正文摘要 |

### 6.2 推荐字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `overview` | object | 否 | 已有 AI 事件概述；若尚未生成，可省略或为空对象 |
| `overview.time` | string | 否 | 事件时间范围或主要发生时间 |
| `overview.location` | string | 否 | 事件地点 |
| `overview.cause` | string | 否 | 事件起因 |
| `overview.persons` | string | 否 | 涉事人物 |
| `timeline` | object[] | 否，可为空数组 | 基础事件时间线，按时间升序 |
| `timeline[].time` | string | 否 | 节点时间 |
| `timeline[].content` | string | 否 | 节点内容 |
| `trend` | number[] | 否，可为空数组 | 趋势数值数组 |
| `trend_labels` | string[] | 否，可为空数组 | 趋势横轴标签，长度应与 `trend` 一致 |
| `trend_highlights` | number[] | 否，可为空数组 | 趋势图中需要高亮的点位下标；第一版可不提供 |
| `platform_distribution` | object[] | 否，可为空数组 | 平台分布 |
| `platform_distribution[].name` | string | 否 | 平台名称 |
| `platform_distribution[].value` | number | 否 | 平台数量或占比 |

### 6.3 增强可选字段

以下字段不作为第一版阻塞项。没有这些字段时，5 号仍然必须返回结果，但应降低 `confidence`，并在 `warnings` 或 `limitations` 中说明限制。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `articles[].platform` | string/null | 平台名称 |
| `articles[].author` | string/null | 作者或账号 |
| `articles[].account_id` | string/null | 平台账号 ID |
| `articles[].account_name` | string/null | 平台账号名称 |
| `articles[].account_type` | string/null | 账号类型，如普通用户、大V、媒体、官方机构 |
| `articles[].is_official` | boolean/null | 是否官方来源 |
| `articles[].crawl_time` | string/null | 采集时间 |
| `articles[].repost_count` | number/null | 转发量或转载量 |
| `articles[].comment_count` | number/null | 评论量 |
| `articles[].like_count` | number/null | 点赞量 |
| `articles[].reference_urls` | string[] | 正文引用链接 |
| `articles[].quoted_news_ids` | int[] | 引用或转述的新闻编号 |
| `articles[].parent_news_id` | int/null | 父级新闻编号 |
| `articles[].duplicate_group_id` | string/null | 重复或同源内容分组 |
| `propagation_inputs` | object/null | 真实传播图输入；第一版不强制 |
| `propagation_inputs.nodes` | object[] | 传播节点 |
| `propagation_inputs.edges` | object[] | 传播边 |
| `enhancement` | object | 字段可用性标记，便于 5 号降级 |

降级规则：

- 基础必需数组暂时无法提供时，1 号传空数组。
- 推荐字段暂时无法提供时，可以省略或传空数组、空对象、空字符串。
- 增强字段暂时无法提供时，可以省略。
- 5 号收到空数组、空字符串或缺失增强字段时，必须说明信息不足或降低置信度，不得编造。

### 6.4 新增字段负责人和生成方式

| 字段 | 负责人 | 如何生成 | 5 号是否可生成 | 说明 |
| --- | --- | --- | --- | --- |
| `articles` | 1 号 | 根据 `event_id` 查询事件下相关新闻并组装 | 否 | 事实数据，5 号只能消费 |
| `articles[].news_id` | 1 号 | 后端入库时生成 | 否 | 数据库 ID |
| `articles[].title/content/source/url/publish_time` | 3 号提供，1 号保存 | 采集与清洗阶段产生 | 否 | 事实来源，5 号不得补造 |
| `timeline` | 1 号基础生成，5 号可临时整理。1 号若暂未生成，可传空数组；5 号可基于 `articles` 临时整理，但必须说明限制 | 取事件下所有 articles。按 publish_time 升序排序。每条新闻生成一个节点。content 先用新闻标题。如果同一时间段新闻太多，1号可以只取最早、热度最高、来源最权威的几条；没有排序能力时先全量返回也可以。 | 可生成分析用临时时间线 | 第一版 timeline 不是 AI 生成字段；5 号临时整理的 timeline 只用于分析，不写回事实表 |
| `overview` | 5 号生成，1 号保存/返回，4 号提供 NLP 支撑 | 5 号基于 `title`、`summary`、`articles`、`timeline`、`keywords` 生成；1 号再次调用 5 号时可把已保存的 overview 带回上下文 | 是 | 属于 AI 派生字段；不得编造地点、人物、起因 |
| `trend` / `trend_labels` | 1 号 | 基于历史热度、报道量或事件快照统计 | 否，只能解释 | 没有趋势数据时，5 号不得判断升温/降温 |
| `trend_highlights` | 1 号，可选 | 基于 `trend` 数组用规则标出起点、峰值、最新点或明显变化点 | 否，只能解释 | 第一版可传空数组，前端也可自行计算 |
| `platform_distribution` | 1 号为主，依赖 3 号来源字段 | 按平台或来源统计 | 否，只能解释 | 没有平台字段时可为空数组 |
| `propagation_inputs` | 1 号可选生成，依赖 3 号采集字段 | 根据转载、引用、父子关系整理真实传播图 | 否，只能消费 | 第一版不强制 |
| 账号与互动量字段 | 3 号可选提供，1 号保存 | 采集平台账号、转发、评论、点赞等信息 | 否 | 没有时不阻塞 |
| `ai_report` | 5 号生成，1 号保存/返回 | 基于事件上下文生成 | 是 | AI 派生字段 |
| `authenticity` | 5 号生成，1 号保存/返回 | 基于来源、正文、URL、时间、多来源一致性判断 | 是 | AI 派生字段，不是事实裁定 |
| `propagation_analysis` | 5 号生成，1 号保存/返回 | 基于 `timeline`、`articles` 和可选 `propagation_inputs` 分析 | 是 | 缺少真实传播图时只能弱分析 |
| `propagation_path` | 5 号生成，1 号返回给前端 | 从 `propagation_analysis.path` 简化生成 | 是 | 用于前端路径展示 |

### 6.5 新增字段详细生成规则

本节用于避免新增字段被误解为其他成员必须额外完成的复杂算法。第一版优先采用可由现有数据直接统计、排序或拼装的规则；无法生成时允许返回空数组、空对象或 `null`，5 号必须据此降级。

#### 6.5.1 `timeline`

负责人：1 号。

输入来源：

- `articles.news_id`
- `articles.title`
- `articles.source`
- `articles.url`
- `articles.publish_time`

生成方法：

1. 1 号根据 `event_id` 查询该事件下全部文章。
2. 过滤没有 `publish_time` 的文章；若全部缺失，则返回空数组。
3. 按 `publish_time` 升序排序。
4. 每篇文章生成一个节点：

```json
{
  "time": "2026-07-08 10:00:00",
  "content": "新闻标题",
  "news_id": 1001,
  "source": "人民网",
  "url": "https://example.com/news/1001"
}
```

5. 第一版 `content` 直接使用新闻标题，不要求 1 号做文本摘要。
6. 如果同一时间段文章过多，1 号可只保留最早、来源更权威或热度更高的若干条；没有筛选能力时可全量返回。

降级规则：

- 没有文章或没有发布时间时，返回 `[]`。
- 5 号可以基于 `articles` 临时整理分析用时间线，但不得写回事实表，也不得声称该时间线是后端确认的事实时间线。

#### 6.5.2 `trend` 与 `trend_labels`

负责人：1 号。

含义：

- `trend` 是趋势图纵轴数值数组。
- `trend_labels` 是趋势图横轴标签数组。
- 二者长度必须一致。

第一版推荐生成方法：按报道量统计。

1. 1 号根据 `event_id` 查询该事件下全部文章。
2. 读取 `articles.publish_time`。
3. 根据事件时间跨度选择分桶粒度：
   - 事件跨度小于等于 48 小时：按小时分桶。
   - 事件跨度大于 48 小时：按天分桶。
4. 每个时间桶统计文章数量，作为 `trend` 的一个数值。
5. 每个时间桶的时间文本作为 `trend_labels`。

示例：

```json
{
  "trend_labels": ["07-08 10:00", "07-08 11:00", "07-08 12:00"],
  "trend": [2, 5, 3]
}
```

可选增强生成方法：按热度统计。

- 如果 4 号已经为文章生成 `analysis.heat_score`，1 号可以按同一时间桶聚合 `heat_score`。
- 聚合方式必须固定为一种，建议第一版使用平均值：

```text
某时间桶 trend 值 = 该时间桶内所有文章 heat_score 的平均值
```

禁止规则：

- 5 号不得自行生成结构化 `trend` 数组。
- 没有 `trend` 或 `trend_labels` 时，5 号不得判断“升温”“降温”“出现拐点”。

降级规则：

- 文章数量不足或发布时间缺失时，1 号返回 `trend: []`、`trend_labels: []`。
- 如果只基于报道量统计，5 号在解释时应表述为“报道量趋势”，不得表述为完整舆情热度趋势。

#### 6.5.3 `trend_highlights`

负责人：1 号可选生成，2 号也可在前端自行计算。

含义：

`trend_highlights` 是 `trend` 数组中需要高亮显示的点位下标，不是新的趋势数据。

生成方法：

1. `trend` 为空时，返回 `[]`。
2. `trend` 非空时，可按以下规则取下标并去重：
   - 第一个非零点。
   - 最大值点。
   - 最后一个点。
   - 当前值比前一个值增长超过 50% 的点。
   - 当前值比前一个值下降超过 50% 的点。

示例：

```json
{
  "trend": [2, 4, 10, 8, 3],
  "trend_highlights": [0, 2, 4]
}
```

降级规则：

- 第一版可以不提供该字段，或返回 `[]`。
- 5 号不得根据 `trend_highlights` 反推不存在的事实进展。

#### 6.5.4 `platform_distribution`

负责人：1 号生成，依赖 3 号采集字段。

输入来源优先级：

1. 优先使用 `articles.platform`。
2. `platform` 为空时使用 `articles.source`。
3. 两者都为空时归为 `未知来源`，也可以在第一版直接忽略该文章。

生成方法：

1. 1 号根据 `event_id` 查询事件下全部文章。
2. 对每篇文章确定平台名：

```text
platform_name = articles.platform 非空 ? articles.platform : articles.source
```

3. 按 `platform_name` 分组计数。
4. 输出数组：

```json
[
  {
    "name": "微博",
    "value": 32
  },
  {
    "name": "新闻网站",
    "value": 25
  }
]
```

约束：

- `value` 第一版统一表示数量，不表示百分比。
- 如果前端需要百分比，由前端基于数量自行计算。
- 如果 3 号暂时无法提供 `platform`，1 号可以使用 `source` 近似统计。

降级规则：

- 没有平台或来源数据时返回 `[]`。
- 5 号只能解释该字段，不能补造平台分布。

#### 6.5.5 账号与互动量字段

负责人：3 号可选提供，1 号保存。

字段包括：

- `author`
- `account_id`
- `account_name`
- `account_type`
- `is_official`
- `repost_count`
- `comment_count`
- `like_count`

生成方法：

1. 3 号在采集页面时，如果页面存在作者、账号、点赞、评论、转发等信息，则按原值采集。
2. 如果页面没有这些信息，统一传空字符串、`null` 或 `0`。
3. `account_type` 第一版不要求复杂识别，可使用简单规则：
   - 来源或账号名称包含“官方”“政府”“警方”“发布”等关键词，可标为 `官方机构`。
   - 来源属于人民网、新华社、央视新闻等媒体，可标为 `媒体`。
   - 无法判断时为空字符串。
4. `is_official` 第一版可由 3 号或 1 号基于白名单、来源名称或账号名称判断；无法判断时为 `false` 或 `null`。

约束：

- 这些字段均为增强可选字段。
- 缺失时不阻塞 5 号问答、报告、真实性判断或传播分析。
- 5 号不得自行补造账号 ID、互动量或官方身份。

#### 6.5.6 `reference_urls`、`quoted_news_ids` 与 `parent_news_id`

负责人：

- `reference_urls`：3 号可选提供。
- `quoted_news_ids`：1 号可选生成。
- `parent_news_id`：3 号可提供原始线索，1 号最终确认保存。

生成方法：

1. 3 号从文章正文、页面引用区或转载说明中提取 URL，形成 `reference_urls`。
2. 1 号将 `reference_urls` 与数据库中已有 `articles.url` 匹配。
3. 匹配成功的文章 ID 写入 `quoted_news_ids`。
4. 如果某篇文章明确转载、引用或跟进另一篇已入库文章，1 号可以将被引用文章写为 `parent_news_id`。
5. 如果只能判断多篇文章属于同一事件，不能判断父子关系，则不得强行填写 `parent_news_id`。

降级规则：

- 无引用链接时，`reference_urls` 为空数组。
- 无法匹配数据库文章时，`quoted_news_ids` 为空数组。
- 无法确认父级文章时，`parent_news_id` 为 `null`。

#### 6.5.7 `duplicate_group_id`

负责人：1 号为主，4 号相似度结果可辅助。

生成方法：

1. 1 号优先按 `url` 去重，完全相同 URL 视为同组。
2. URL 不同但标题高度相似时，可结合 4 号 `similar_news` 判断是否同源或重复。
3. 确认为同源或重复后，由 1 号生成同一个 `duplicate_group_id`。
4. 第一版如果没有稳定去重逻辑，可以为空。

约束：

- `duplicate_group_id` 只表示“疑似同源或重复内容分组”，不表示传播父子关系。
- 5 号只能消费该字段，不能生成或覆盖。

#### 6.5.8 `propagation_inputs`

负责人：1 号可选生成。

含义：

`propagation_inputs` 是提供给 5 号的真实传播图输入，不是 5 号生成结果。它用于增强 `propagation_analysis` 的可靠性。

生成方法：

1. 节点 `nodes` 来自事件下文章：

```json
{
  "id": "news_1001",
  "news_id": 1001,
  "label": "人民网",
  "time": "2026-07-08 10:00:00",
  "type": "media",
  "url": "https://example.com/news/1001"
}
```

2. 边 `edges` 优先来自明确关系：
   - `parent_news_id`
   - `quoted_news_ids`
   - `reference_urls` 匹配结果
3. 如果没有明确父子或引用关系，第一版不应仅凭发布时间强行生成真实传播边。
4. 只有“同一事件下按发布时间排列”的弱顺序时，应交给 5 号在 `propagation_analysis.limitations` 中说明，而不是写成真实传播图。

降级规则：

- 没有明确传播关系时，`propagation_inputs` 可以为 `null`。
- 5 号可以基于 `articles.publish_time` 和 `timeline` 生成“已知报道顺序路径”，但必须降低 `confidence`，并说明不是完整真实传播链。

## 7. 数据库存储设计建议

本节为 1 号后端数据库设计建议，用于承接 3 号采集数据、4 号 NLP 输出和 5 号 AI 派生结果。

设计原则：

1. 核心业务字段结构化保存。
2. AI 生成结果和复杂增强字段优先使用 JSON 保存，避免频繁改表。
3. 5 号不直接读写数据库，所有保存由 1 号负责。
4. 3 号、4 号、5 号只提供各自输出，1 号负责入库、关联和对外返回。

### 7.1 新闻表 `articles`

保存 3 号采集与清洗后的新闻事实数据。

| 字段 | 类型 | 是否必填 | 来源 | 说明 |
| --- | --- | --- | --- | --- |
| `news_id` | int / bigint | 是 | 1 号 | 新闻唯一编号 |
| `event_id` | int / bigint / null | 否 | 1 号 | 所属事件编号；第一版可直接回填，复杂场景建议使用关系表 |
| `title` | varchar / text | 是 | 3 号 | 新闻标题 |
| `content` | text | 是 | 3 号 | 新闻正文或摘要 |
| `source` | varchar | 是 | 3 号 | 来源媒体、网站或发布主体 |
| `url` | varchar / text | 是 | 3 号 | 原文链接 |
| `publish_time` | datetime | 是 | 3 号 | 新闻发布时间 |
| `crawl_time` | datetime | 否 | 3 号 | 采集时间 |
| `platform` | varchar | 否 | 3 号 | 平台，如新闻网站、微博、公众号 |
| `author` | varchar | 否 | 3 号 | 作者或发布账号 |
| `account_id` | varchar | 否 | 3 号 | 平台账号 ID |
| `account_name` | varchar | 否 | 3 号 | 平台账号名称 |
| `account_type` | varchar | 否 | 3 号 / 1 号 | 普通用户、大V、媒体、官方机构等 |
| `is_official` | boolean | 否 | 3 号 / 1 号 | 是否官方来源 |
| `repost_count` | int | 否 | 3 号 | 转发量或转载量 |
| `comment_count` | int | 否 | 3 号 | 评论量 |
| `like_count` | int | 否 | 3 号 | 点赞量 |
| `reference_urls` | json / text | 否 | 3 号 | 正文引用链接 |
| `quoted_news_ids` | json / text | 否 | 1 号 | 由 `reference_urls` 匹配库内文章后生成的被引用新闻编号数组 |
| `parent_news_id` | int / bigint | 否 | 3 号 / 1 号 | 父级新闻编号，用于传播链 |
| `duplicate_group_id` | varchar | 否 | 1 号 / 4 号 | 同源或重复内容分组 |
| `created_at` | datetime | 是 | 1 号 | 入库时间 |

说明：

- `title`、`content`、`source`、`url`、`publish_time` 是基础字段。
- 第一版可以通过 `articles.event_id` 表示新闻所属事件。
- 账号、互动量、引用关系字段是增强可选字段，缺失时不阻塞第一版。
- 5 号不能生成或补造 `articles` 中的事实字段。

### 7.2 事件表 `events`

保存 1 号聚合后的事件级基础数据。

| 字段 | 类型 | 是否必填 | 来源 | 说明 |
| --- | --- | --- | --- | --- |
| `event_id` | int / bigint | 是 | 1 号 | 事件唯一编号 |
| `title` | varchar / text | 是 | 1 号 | 事件标题 |
| `summary` | text | 是 | 1 号 | 事件摘要 |
| `heat` | float | 是 | 1 号 / 4 号 | 事件级热度，由 `heat_score` 聚合或映射 |
| `risk_level` | varchar | 是 | 4 号 | `低` / `中` / `高` |
| `stage` | varchar | 是 | 4 号 | `萌芽期` / `成长期` / `高潮期` / `衰退期` |
| `create_time` | datetime | 是 | 1 号 | 事件创建时间 |
| `update_time` | datetime | 是 | 1 号 | 事件更新时间 |
| `status` | varchar | 否 | 1 号 | 事件状态，如 active / closed |
| `extra` | json / text | 否 | 1 号 | 预留扩展字段 |

说明：

- `overview` 不建议放入 `events` 主表作为事实字段，因为 3.0 中 `overview` 定义为 5 号 AI 派生结果。
- `risk_level` 和 `stage` 来自 4 号分析结果，5 号只能解释，不能重新计算。
- `timeline`、`trend`、`trend_labels`、`trend_highlights`、`platform_distribution` 第一版可由 1 号查询时动态生成；如果需要缓存，可放入 `extra`，不强制新增独立表。

### 7.3 事件-新闻关系表 `event_article_relations`

保存事件与新闻之间的关联关系。

| 字段 | 类型 | 是否必填 | 来源 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | int / bigint | 是 | 1 号 | 主键 |
| `event_id` | int / bigint | 是 | 1 号 | 事件编号 |
| `news_id` | int / bigint | 是 | 1 号 | 新闻编号 |
| `relation_type` | varchar | 否 | 1 号 | original / similar / repost / reference 等 |
| `created_at` | datetime | 是 | 1 号 | 建立关系时间 |

说明：

- 第一版也可以在 `articles` 表中使用 `event_id` 简化实现。
- 若考虑一篇新闻关联多个事件，建议使用本关系表。

### 7.4 NLP 分析表 `analysis`

保存 4 号 NLP 分析输出。

| 字段 | 类型 | 是否必填 | 来源 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | int / bigint | 是 | 1 号 | 主键 |
| `news_id` | int / bigint | 是 | 4 号输入对应 | 新闻编号 |
| `event_id` | int / bigint | 否 | 1 号 | 聚合后回填事件编号 |
| `keywords` | json / text | 是 | 4 号 | 关键词数组 |
| `positive` | float | 是 | 4 号 | 正面比例，0~1 |
| `neutral` | float | 是 | 4 号 | 中性比例，0~1 |
| `negative` | float | 是 | 4 号 | 负面比例，0~1 |
| `heat_score` | float | 是 | 4 号 | 热度得分 |
| `stage` | varchar | 是 | 4 号 | 生命周期 |
| `risk_level` | varchar | 是 | 4 号 | 风险等级 |
| `similar_news` | json / text | 否 | 4 号 | 相似新闻 ID 数组 |
| `created_at` | datetime | 是 | 1 号 | 保存时间 |

说明：

- 第一版按新闻级分析结果保存。

1. 事件首次生成且尚无 AI 报告。
2. 事件 `update_time` 发生变化。
3. 1 号后端人工或定时任务主动触发刷新。

## 16. 超时和失败处理

### 16.1 AI 问答失败

如果 5 号 AI 模块调用失败，1 号返回：

```json
{
  "code": 503,
  "message": "AI服务暂不可用，请稍后重试",
  "data": null
}
```

### 16.2 AI 分析生成失败

事件详情接口不得因为 AI 事件概述、AI 报告、虚假文本检测或传播路径分析失败而整体失败。

如果基础事件数据可用但 AI 分析失败，1 号返回：

```json
{
  "overview": null,
  "ai_report": null,
  "authenticity": null,
  "propagation_analysis": null,
  "propagation_path": []
}
```

并在后端记录失败原因。

### 16.3 超时

AI 问答、报告生成、虚假文本检测和传播路径分析建议超时时间为 30 秒。

超时后按 AI 服务不可用处理。
